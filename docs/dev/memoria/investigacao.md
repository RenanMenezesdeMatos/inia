### Tools de investigação operacional para Agents (2026-09-17, migration 074)

Regra: **TOOL consulta/calcula fatos determinísticos; AGENT decide o que investigar, formula hipóteses e interpreta; ORQUESTRADOR escolhe especialistas e sintetiza; WORKFLOW define objetivo/escopo e pode RESTRINGIR capacidades; CHAT/AVATAR acionam Orquestrador + Agents sem Workflow.** A IA não faz cálculo que a aplicação faz e não conclui causa sem evidência. Módulo `backend/src/modules/investigation`: `domain/capabilities.ts` (7 capacidades amigáveis — INDICATOR_ANALYSIS, SEGMENTATION, OPERATIONAL_COMPARISON, INTERACTION_ANALYSIS, WORK_CONTEXT, KNOWLEDGE, SUPPORT_MATERIALS; `effectiveCapabilities = agent ∩ workflowAllowed`, o Workflow nunca concede), `domain/tool-catalog.ts` (19 Tools: definição única = declaração de function calling + zod dos argumentos + capacidade + rótulo; nunca "diagnose_everything"), `domain/tool-output.ts` (toda Tool devolve `data` + `quality {status,sampleCount,coverage,freshness}` + `provenance {period,population,filters,dataSource,method}`), `domain/tool-trace.ts` (`ToolInvocationTrace`: só fatos/ações observáveis — nunca prompt nem raciocínio), `domain/analysis-dimensions.ts` (catálogo: DAY/DAY_OF_WEEK/WEEK pela medição; SUBJECT/CHANNEL/HOUR/FLAG pelas interações — proxy declarada por UNIDADE: SECONDS ↔ duração, COUNT ↔ volume; PERCENT = não suportado; não existe medição ↔ interação), `domain/anomaly-detection.ts` (mediana + MAD×1,4826, escala mínima 2% da baseline, |z|≥3 anomalia, ≥30% fora = recorrente). `application/investigation-runtime.ts` = loop com `generateWithTools` (Gemini function calling): política de raciocínio no prompt (`INVESTIGATION_POLICY`), orçamento 12 chamadas (`DEFAULT_MAX_TOOL_CALLS`), cache por execução (mesma Tool + mesmos argumentos), timeout por Tool/investigação, trace, `renderDossier` (fatos F1..Fn + "NÃO INVESTIGADO" + notas do modelo) que entra no input da chamada FINAL — os contratos/parsers de resposta (`STRUCTURED_OUTPUT_INSTRUCTIONS*`, verbatim da evidência, materiais) continuam os de sempre. Tools em `application/tools/` reutilizam o resolvedor único de medições (`resolveOperationalWindow[BySubject]`, novo `resolveOperationalDailySeries`, `mergeRawComponents` no domínio de agregação), fechamento oficial como fornecido (nunca recalculado), `resolveWorkdaysBySubject` (jornada, precedência congelada), `retrieveKnowledgeForAgent` e `selectSupportMaterialRecommendations` (Materiais de apoio V1). Sujeito da investigação sempre do runtime (`loadSubject`: org verificada), nunca do modelo; pares só agregados com população mínima 4 (`MINIMUM_COMPARISON_POPULATION`); comparáveis por regra determinística (mesmo assunto/canal, menor duração), anônimas; análise de transcrição (`analyze_interactions`/`analyze_peer_patterns`) usa LLM mas descarta trecho não literal por código. Integração: `agents.investigation_capabilities text[]` (editor: card "Ferramentas de investigação", Collapsible avançado só leitura), `run-agent.ts` (`allowedCapabilities`, `subject`, `now`; período padrão = janela do Workflow com datas inclusivas no rótulo; `toolTrace`/`investigation` no topo de `AgentRunOutcome`/`AgentWorkflowResult`), `run-specialist-tool.ts` (capacidades do PRÓPRIO especialista; `options.investigation` = interação/indicador do enrollment), `OrchestratedReply.results[].toolTrace`, node CALL_AGENT `allowedCapabilities` ("Ferramentas nesta execução" — ausente = as do Agent), `agent_runs.tool_trace` (074), `feedbacks.context_snapshot.toolTrace/investigation` (`feedback-investigation-trace.ts`, transportado pelo Output sempre), `assistant_interactions.tool_calls[].toolTrace` (chat/voz), Revisão humana ("Ferramentas de investigação utilizadas"), QA Lab (`StepToolTrace` "Ferramentas utilizadas"). `callAgentForIndicator*` passou a resolver meta pessoa > Subgrupo > Grupo (`resolveOperatorTarget`) e `parseJsonOutput` tolera texto em volta do JSON. Demo: Subgrupo "Diagnóstico IA — Operadores com gravações" (equipe do Supervisor 01, `DIAGNOSTIC_SUBGROUP`, idempotente) + artefatos `[POC TOOLS]` e 6 Feedbacks etiquetados `context_snapshot.pocTools` — ver docs/dev/massa-demo.md; runner `backend/scripts/poc-tools/run-poc-feedbacks.ts` (rascunho pelo motor real, Revisão auto-aprovada), `dry-run-investigation.ts` (inclusive baseline sem Tools). Provas: `investigation/domain/*.test.ts`, `investigation-runtime.test.ts`, `run-agent-investigation.test.ts`, `run-specialist-tool.test.ts`, `output-executor.test.ts`, `review-content.test.ts`, `INIA_DB_PROOF=1 npx vitest run investigation-tools-proof` (17). Limitações: só as dimensões acima; Orquestrador pós-JOIN não investiga; node Orquestrador não restringe capacidades; a investigação costuma esgotar o orçamento de 12 (o dossiê lista o que NÃO foi investigado). ### Investigação V1.1 — eficiência (2026-09-17, sem migration)

Princípio: **evidência útil por token** — o Agent pensa menos vezes sobre as mesmas coisas, sem perder investigação útil. Sem Tool nova, sem mudança arquitetural. O que mudou em `investigation/application/investigation-runtime.ts`: (1) **preflight determinístico** (rodada 0): execução por indicador roda `get_indicator_snapshot` + `validate_data_quality` + `get_available_dimensions` (e conta interações do período) antes da 1ª request; por interação roda `get_interaction_context` — só fato inicial, nunca diagnóstico; (2) **ondas paralelas**: o Gemini devolve N function calls numa resposta e o runtime executa em `Promise.all` (orçamento reservado de forma síncrona, `sequence` lógica, `round`/`concurrency` no trace, cache por promessa cobre duplicatas na mesma onda); (3) **Evidence Ledger** (`domain/evidence-ledger.ts`, F1..Fn compactos: Tool + argumentos essenciais + resumo + qualidade; sem UUID/timestamp/`method`) é o que o modelo lê; o trace completo continua persistido com `ledgerRef`; (4) **compactação por rodada**: cada request recebe objetivo + contexto inicial + ledger + limitações + detalhe SÓ da última onda + orçamento — um único turno de usuário, nunca o histórico de function calls (também evita `thoughtSignature`); (5) **pruning por rodada** (`application/tool-phases.ts`): só Tools das capacidades efetivas, aplicáveis ao contexto (sem interações → nenhuma Tool de interação) e com pré-requisito satisfeito (analyze_* só com ids conhecidos; peer/comparáveis só com assunto conhecido); `synthesize_evidence`/`recommend_support_materials` nunca são declaradas — organização de evidências e seleção de materiais (mesma validação V1) acontecem na síntese final; (6) limites: `TARGET_TOOL_CALLS` 8, teto 12 (preflight conta), `DEFAULT_MAX_PLANNING_ROUNDS` 3 (política pede 2), notas/síntese não contam; (7) política de valor informacional no prompt (SUBGRUPO antes de GRUPO, uma camada de histórico, dimensão com hipótese, jornada/KB sob demanda, reserva para interações antes de afirmar comportamento); prefixo estático primeiro (system → política → capacidades → sujeito) para cache do provider.

**Evidence gating (por código, `domain/evidence-gating.ts`, aplicado em `run-agent.ts › synthesizeWithGating`)**: a chamada final estruturada devolve também `supportedHypotheses/unsupportedHypotheses/limitations/behavioralClaims[{text, evidenceRefs}]/recommendationSupport[{text, basis: OBSERVED_EVIDENCE|KNOWLEDGE_GUIDANCE|GENERAL_DEVELOPMENT_SUGGESTION, evidenceRefs}]` (internos — não vão ao colaborador). Afirmação comportamental exige ref de fato de interação/transcrição (`BEHAVIORAL_EVIDENCE_TOOLS`, ou `TRANSCRICAO` no feedback de chamada); OBSERVED_EVIDENCE exige ref do ledger; KNOWLEDGE_GUIDANCE exige base real. Violação → UMA re-request corretiva; persistindo → `AGENT_UNSUPPORTED_BEHAVIORAL_CLAIM` (execução FAILED, como a evidência não literal). Persistido em `InvestigationSummary.synthesis/evidenceGating` (→ `context_snapshot.investigation`, QA Lab "Evidência da síntese"). A checagem verbatim normaliza aspas (o modelo troca "…" por '…' ao escapar JSON) e o contrato lembra que `evidenceFound` mantém os rótulos originais (nunca "Você:").

**Telemetria (produto, não script)**: `LlmCallRecord` ganhou `cachedInputTokens`/`reasoningTokens` (Gemini `cachedContentTokenCount`/`thoughtsTokenCount`, null = não informado, NUNCA estimado), `phase` (`withLlmPhase`: PLANNING/SEMANTIC_ANALYSIS/SYNTHESIS…), `toolCalls`, `promptBreakdown` (chars de sistema/schemas/entrada). `generateWithTools`/`generateAgentReplyWithUsage` devolvem `usage`; o runtime soma tudo (inclusive analyze_* e a síntese final) em `InvestigationSummary.requests/tokens/tokenBudget` (limiares de AVISO `INVESTIGATION_TOKEN_WARNING_TOTAL/INPUT/OUTPUT`, padrão 60k/50k/8k — nunca teto). QA Lab: `trace.telemetry` (`qa-lab/domain/qa-run-telemetry.ts`) calculado por código a cada insert/update — requests, tokens (input/cached/uncached/output/reasoning/total), cacheHitRate, toolBudget (executadas/cache/recusadas/preflight/rodadas/ondas/outcome), tokenBudget, fases, perRequest e `reference` = run compatível anterior (mesmo recurso + `context.operator.id` + `context.interaction.id`, não RUNNING/FAILED; run antigo vale com as colunas de totais e Tool calls contadas do trace). Histórico lista Requests IA · Tool calls · Rodadas · Input · Cached · Uncached · Output · Reasoning · Total · Duração · Tool Budget · Token Budget; detalhe tem a aba "Tokens e eficiência" (total, antes × depois com deltas, por fase, por request). Runs antigos continuam legíveis ("Não informado"). Benchmark: `POC_TAG_PREFIX=POC_EFFICIENCY_V1` no runner (ver docs/dev/massa-demo.md). Wiki: `/wiki/agents/ferramentas-investigacao#eficiencia`, `/wiki/qa-lab#tokens-eficiencia`.

### Investigação V1.2 — hardening: três contextos, handles, escopo de evidência, gating em toda resposta e roteamento de modelo (2026-09-18, sem migration)

Princípio: **UUID é para o sistema; fato é para a IA; trace completo é para auditoria; resumo é para o humano; modelo caro só quando a tarefa justifica.** Três contextos que nunca se misturam: **AUDIT** (persistido: `toolTrace` com `argumentsSummary` = ids reais e `modelArguments` = como o modelo pediu, `investigation.handles` = mapa handle → id, proveniência integral) ≠ **MODEL** (só o que raciocina: ledger F-n, qualidade, período; `investigation/domain/handle-registry.ts` — `HandleRegistry` escopado à execução: `I1` interação, `K1` documento, `M1` material; `projectForModel` troca ids por handles e remove `TECHNICAL_KEYS` (org/pessoa/time/measurementIds/timestamps); `resolveModelArgs` converte handles → ids reais antes de qualquer acesso a banco e RECUSA handle desconhecido/UUID nunca visto nesta execução (`UNKNOWN_HANDLE`, nunca cross-execution/cross-org); materiais de apoio também por handle (`M1` posicional entre os candidatos — `supportMaterialHandle`/`resolveSupportMaterialHandle`); `LlmPromptBreakdown.technicalIds` conta UUIDs por request e o QA Lab prova 0) ≠ **HUMAN REVIEW** (`pending-actions/domain/review-presentation.ts` → `buildReviewPresentation`: DTO legível — resultado, indicador, evolução/comparação vindas do ledger, evidências F-n, limitações, afirmações com escopo/representatividade, base das recomendações, materiais, resumo das ferramentas — exposto em `HumanReviewDetail.presentation` e em `QaTrace.pendingReview.presentation`; frontend `components/pending/review-presentation.tsx` com "Ver detalhes técnicos"; a persistência não muda). O único lugar que enviava o "JSON gigante" a um LLM era o resumo consolidado pós-JOIN (`buildConsolidatedSummary` fazia `JSON.stringify(child.nodeOutputs)` com toolTrace/ids/contextSnapshot) — agora passa por `workflows/domain/model-context-projection.ts` (`projectNodeOutputsForModel`, teste prova zero UUID). A Revisão humana em si (Pendências) nunca foi enviada a LLM.

**Orçamento**: `preflightCalls` (rodada 0, da aplicação) não consome `targetToolCalls`/`budget`; `investigationToolCalls` = só as escolhidas pelo Agent; `toolCalls` = total; `MAX_TOTAL_TOOL_CALLS_SAFETY` (16) cobre a soma. **Representatividade** (`domain/evidence-representativeness.ts`, determinística): INSUFFICIENT / ANECDOTAL / REPRESENTATIVE por nº analisado × universo (`interactionsInPeriod`) × amostra mínima (5; 20% do universo; 30 absoluto). **Escopo da claim** (`ClaimScope`: INTERACTION_SPECIFIC | PERIOD_PATTERN | EMPLOYEE_PATTERN | POPULATION_PATTERN; ausente = o mais restrito): `gateSynthesis` exige REPRESENTATIVE para PERIOD/EMPLOYEE e pares representativos para POPULATION — 2 interações sustentam "nas interações analisadas ocorreu X", nunca "você costuma fazer X". **Gating em toda resposta** (`investigation/application/text-evidence-gating.ts`): linha interna `EVIDENCE_JSON:` para texto (especialista TEXT, Agent em texto livre), campos no JSON para FEEDBACK; 1 correção; persistindo → Workflow descarta (`AGENT_UNSUPPORTED_BEHAVIORAL_CLAIM`), chat/voz recebe a versão FACTUAL (`renderFactualFallback`); Orquestrador (`run-orchestrated-reply.ts`) recebe as claims dos especialistas como `C1..Cn` com escopo/representatividade e `gateOrchestratorClaims` impede ampliar escopo (persistindo → síntese factual com as respostas dos especialistas). Refs internas (F-n/M-n/TRANSCRICAO) coladas no texto do colaborador são removidas por código (`stripInternalRefs`). A checagem verbatim aceita trechos literais emendados com reticências (cada segmento ≥ 15 chars literal).

**Model routing** (`shared/application/model-routing/`): `ModelProvider` (GEMINI|OPENAI|XAI|ANTHROPIC|LOCAL), `ModelTier` (BASIC|STANDARD|DEEP), `ModelProfile` (capacidades/janela), registry com perfis padrão (BASIC = gemini-3.1-flash-lite, STANDARD = gemini-3.8-flash, DEEP = mesmo modelo do STANDARD por falta de modelo mais forte configurado — a razão da rota diz isso) e override por `INIA_MODEL_PROFILES` (JSON); `route-policy.ts` decide por sinais do runtime (nunca por LLM), checa capacidade do perfil (tools/saída estruturada/contexto) subindo de tier com `fallback`; `escalateRoute` só por causa explícita (parse/gating) e só no modo EFFICIENCY (no CURRENT o retry fica no mesmo tier — a escalação para o modelo com raciocínio custou ~10k tokens de reasoning numa correção); `provider-adapter.ts` (registry de adapters; `gemini-provider-adapter.ts` é o único hoje) e `llm-gateway.ts` (`routeFor` + `generateForRoute`) — nenhum `if (gemini)` no domínio. Modo `INIA_MODEL_ROUTING` = CURRENT (padrão: rotas da V1.1) | EFFICIENCY (planejamento BASIC; análise semântica/sínteses STANDARD; DEEP por transcrições/multidomínio/conflito/saída complexa). Telemetria: `LlmCallRecord.route` (provider/tier/reason/mode/escalated/fallback), `contextBreakdown` (chars por categoria — `withLlmContext`), `InvestigationSummary.requestLog`; QA Lab mostra rota por request, IDs técnicos, contexto por categoria, preflight × Agent × total. A/B (6 casos, tags `POC_V12_*` = CURRENT e `POC_V12_ROUTING_*` = EFFICIENCY): tokens equivalentes (~29–38k), sem ganho de qualidade comprovado → EFFICIENCY NÃO adotado como padrão. Wiki: `/wiki/agents/ferramentas-investigacao#contexto-modelo|#escopo-evidencia|#roteamento`, `/wiki/qa-lab#tokens-eficiencia`, `/wiki/workflows/human-review`.

### Investigação V1.3 — fail-closed, dois universos, gateway único, prompt por componentes, cache e custo (2026-09-18, sem migration)

Regra: **QUALIDADE > ECONOMIA DE TOKENS** — nenhuma otimização vira padrão porque "parece melhor"; só depois do A/B nos mesmos 6 casos (`POC_V13_CTRL` × `POC_V13_SCHEMA` × `POC_V13_PROMPT` × `POC_V13`, ver docs/dev/massa-demo.md) com fatos essenciais preservados, Tools equivalentes, zero regressão de gating. O que o código aplica:

- **Evidence Gating FAIL-CLOSED** (`investigation/application/text-evidence-gating.ts`: `gateTextReply`, `gateStructuredReply`, `StructuredGatingError`; `domain/evidence-gating.ts`: `hasSynthesisEnvelope`, `renderEnvelopeCorrection`): envelope ausente/inválido (linha `EVIDENCE_JSON` no texto; `behavioralClaims` como array no JSON) NUNCA vale como "zero claims" — 1 correção pedindo o envelope; persistindo → **SAFE FACTUAL FALLBACK** determinístico no chat/voz/Agent texto livre/Orquestrador (`renderFactualFallback`: só ledger validado + limitações + orientação de KB real; nunca texto comportamental do modelo) e descarte no Workflow (`AGENT_EVIDENCE_ENVELOPE_MISSING`/`AGENT_UNSUPPORTED_BEHAVIORAL_CLAIM`). Nunca um segundo LLM julga o primeiro. `EvidenceGatingResult` ganhou `envelopePresent/parseStatus/correctionAttempted/correctionSucceeded/fallbackUsed/fallbackReason` (QA Lab "Qualidade", Revisão humana "Validação de evidência").
- **Dois universos** (`domain/evidence-representativeness.ts`, `assessRepresentativeness`): universo REGISTRADO (interações gravadas no período → `recordedCoverage`) ≠ universo OPERACIONAL (volume do indicador, capturado do denominador do snapshot em `InvestigationSummary.operationalUniverse`); `universeRelationship` EXACT | PARTIAL | UNKNOWN — cobertura operacional só quando a relação é conhecida, senão "Não determinado" (nunca inferir 30/1.267); amostra abaixo do absoluto frente a universo operacional maior e não vinculado é rebaixada a ANECDOTAL. QA Lab "Cobertura da evidência" mostra disponíveis × analisadas × coberturas × relação × representatividade × claim scope permitido.
- **Gateway único** (`shared/application/model-routing/llm-gateway.ts` — `generateForRoute` exige `classification {phase, purpose, source, semanticType}`, aceita `contextBreakdown`, `promptComponents`, `cache {cacheable, cacheKeyVersion}`; devolve `cache` observado (NONE/IMPLICIT/EXPLICIT) e `cost`): Agent (estruturado, texto livre, sem investigação), especialista, Orquestrador (chat/voz/Workflow), análise semântica, **pós-JOIN** (`synthesis-agent-executor.ts`) e **Orquestrador consolidado** (`orchestrator-executor.ts`) passam por ele. Exceções documentadas no código: Gemini Live (sessão própria no browser; o que ela aciona no backend usa o gateway) e o chat sem Orquestrador (`streamTextReply`, streaming, sem evidência).
- **Prompt por componentes** (`shared/application/prompting/prompt-components.ts`: `PromptComponent {id, version, phases, static}`, `assemblePrompt(phase, components, profile)`, `cacheKeyVersion` = hash dos estáticos): `investigation/application/investigation-prompt.ts` (planejamento/notas; `INVESTIGATION_POLICY_COMPACT` = mesmas regras, sem repetir o que o turno do usuário já diz; planejamento recebe só os TÍTULOS das bases) e `agents/application/agent-synthesis-prompt.ts` (síntese estruturada/texto livre; contrato de evidência dividido em `renderSynthesisContractRules` estático + `renderSynthesisRefsLine` dinâmico). Perfil `INIA_PROMPT_PROFILE`: CURRENT = composição byte a byte da V1.2 (braço de controle); COMPACT = estático no sistema (sem dado de colaborador), dinâmico (sujeito, KB recuperada, materiais, refs) no turno do usuário. `build-system-prompt.ts` devolve `parts` (identity/knowledge/knowledgeTitles/expectations/restrictions).
- **Schemas compactos** (`investigation/domain/tool-declarations.ts`: `toModelDeclaration(tool, {mode, indicatorInFocus})`, `injectRuntimeDefaults`, `renderCommonParametersNote`; `INIA_TOOL_SCHEMA` FULL|COMPACT): descrição curta (quando usar + o que devolve), período/indicador descritos uma vez no prompt, `indicatorCode` opcional com indicador em foco (o runtime injeta; auditoria guarda `modelArguments` como pedido), enums mantidos; validação continua no catálogo/Zod; semântica das 19 Tools intacta. Pruning extra: Tools de período único já executadas no período padrão saem das rodadas seguintes.
- **Prompt cache explícito** (`assistant/infrastructure/gemini-prompt-cache.ts`, só infra; `INIA_PROMPT_CACHE` NONE|EXPLICIT, TTL `INIA_PROMPT_CACHE_TTL_SECONDS`): só o prefixo marcado cacheável pelo gateway (system + tools estáticos), chave = modelo + versão dos componentes + hash do conteúdo; mínimo real da API 1.024 tokens; request com `cachedContent` vai sem systemInstruction/tools (a API recusa repetir); falha → request normal. Dado dinâmico nunca entra em cache compartilhado. Telemetria: `LlmCallRecord.cache {mode, cacheKeyVersion, cachedTokens, hitRate}`.

### Investigação V1.3.1 — Evidence Sufficiency Controller, fatos críticos e fingerprint da massa (2026-09-18, sem migration)

Regra: **a parada da investigação é um controle de SUFICIÊNCIA DA EVIDÊNCIA, nunca de economia** — não existe "usou X Tools → pare" nem "já há texto → pare"; a economia é consequência de eliminar investigação redundante. O que o código aplica:

- **InvestigationObjective** (`investigation/domain/investigation-objective.ts`, `resolveInvestigationObjective` — determinístico, do Workflow/contrato/sujeito/pergunta, nunca do modelo): DESCRIBE_PERFORMANCE | EXPLAIN_INDICATOR_DEVIATION (causal) | FEEDBACK_SINGLE_INTERACTION | IDENTIFY_EMPLOYEE_PATTERN | COMPARE_WITH_POPULATION | PROCESS_AUDIT | MULTI_DOMAIN_DIAGNOSIS, cada um com `requiredScope` (ClaimScope | null = quantitativo basta) e `causal`. Indicador fora da meta → EXPLAIN; dentro da meta ou "qual foi/quanto" → DESCRIBE (o preflight refina); "costuma/padrão/recorrente" → EMPLOYEE_PATTERN; "comparado ao subgrupo" → POPULATION. O objetivo entra no turno do usuário (`renderObjectiveForModel`) e no dossiê.
- **Sufficiency controller** (`domain/evidence-sufficiency.ts`): o modelo PROPÕE STOP com uma declaração compacta na linha `INVESTIGATION_STATE_JSON:` (supportedClaims com escopo/refs, unresolvedQuestions/hypotheses com `material` + `candidateTools`, contradictoryEvidence OPEN|CONTEXTUALIZED, dataLimitations, additionalEvidenceCould…, proposedStopReason — nunca chain-of-thought; `renderStopContract` é componente estático do planejamento). `deriveEvidenceNeeds` (E_INDICATOR_STATE, E_COMPARISON, E_POPULATION, E_BEHAVIORAL_EVIDENCE, E_REPRESENTATIVENESS, E_PROCEDURE + Q-n/H-n declaradas; nunca checklist por indicador) e `evaluateStop` aplicam a regra central: STOP só é aceito com objetivo respondido, escopo exigido sustentado (`scopeAllowedBy`), nenhuma lacuna MATERIAL aberta com Tool disponível (capacidades ∩ pruning), nenhuma contradição OPEN com Tool, limitações registradas. ### Investigação V1.3.4.1 — Relation-Specific Temporal Sufficiency (2026-09-19, sem migration)

Hardening pequeno da V1.3.4 antes do BENCHMARK_BLIND_V4: **AUSÊNCIA NA AMOSTRA ≠ AUSÊNCIA NO UNIVERSO** — "2 de 3 analisadas em B1 × 0 de 3 analisadas em B3 (universo 20)" é uma diferença de AMOSTRA, nunca "deixou de ocorrer em B3". Nada de LLM juiz; tudo determinístico em `investigation/domain/temporal-semantics.ts`:

- **Blocos em dias civis inteiros** (`bucketIndexOf`/`temporalBucketsOf` recebem `dateLabelOf` e dividem a janela por DIAS LOCAIS): cada data local pertence a UM bloco e a legenda model-facing nunca parece sobreposta ("B1 = 2026-06-01 a 2026-06-30 · B2 = 2026-07-01 a 2026-07-31 · B3 = 2026-08-01 a 2026-08-31"; 00:00 local de 01/07 é B2, 23:59:59 de 30/06 é B1). A amostra TEMPORAL_STRATIFIED e a cobertura usam a MESMA divisão (`sampling-strategy.ts`, `temporalCoverageOf`).
- **Contagens por achado × bloco** ganham `universeCount` (interações registradas do colaborador no bloco — `countInteractionsByBucket`, só em janela com > 1 bloco), `coveragePercent`, `zeroMatchedInSample` e `absenceEstablished` (regra `absenceEstablishedBy`: cobertura total do bloco, ou ≥ 5 analisadas cobrindo ≥ 50 % do universo; sem universo = nunca). Amostra de 1 transcrição só é comparável quando é o universo do bloco.
- **Requisito por relação** (`validateRelation` → `relationValidationStatus` SUPPORTED | SAMPLE_DIFFERENCE_ONLY | INSUFFICIENT_EVIDENCE | UNSUPPORTED, com `relationValidationReason`; `directionSupported` = SUPPORTED): INCREASED/DECREASED/CHANGED exigem evidência positiva comparável nos dois blocos ou ausência ESTABELECIDA no lado zero; STABLE considera todos os blocos do intervalo (intermediário sem análise = INSUFFICIENT; ausente = não estável); CONCENTRATED = presente em exatamente um bloco analisado com ausência estabelecida nos contrastes (senão "observado só na amostra de B1"); DIFFERENT_PATTERN = achado A positivo antes e achado B (`contrastFindingIndex`, declarado ou derivado) positivo depois, sem exigir ausência; `trendSupported` (INCREASED/DECREASED) = ≥ 3 momentos ordenados no mesmo sentido quando a janela tem ≥ 3 blocos. Status da comparação: novo `SAMPLE_DIFFERENCE_ONLY` (só da aplicação: comparação realizada, nada sustentado — satisfaz E_TEMPORAL_COMPARISON, não autoriza generalizar); DIFFERENCE_OBSERVED é rebaixado a SAMPLE_DIFFERENCE_ONLY/INSUFFICIENT; NO_DIFFERENCE_SUPPORTED só cai quando uma ausência ESTABELECIDA o contradiz. Ledger: "COMPARAÇÃO TEMPORAL B1×B3: diferença SÓ NA AMOSTRA, não sustentada — achado 1 B1 2 de 3 analisada(s) (universo 12) × B3 0 de 3 (universo 20) (…não afirme 'deixou de ocorrer'…)".
- **Gating por relação** (`gateTemporalClaim`): EARLIER_VS_LATER/CHANGE aceitam fato de amostra SÓ com escopo INTERACTION_SPECIFIC e sem linguagem de relação de período (léxico ganhou "deixou de ocorrer", "não ocorre mais", "concentrado no início/fim…"); senão `SAMPLE_DIFFERENCE_ONLY` (novo motivo). TREND exige ≥ 3 blocos declarados numa janela de ≥ 3 e finding com `trendSupported`; STABILITY exige todos os blocos analisados comparados e declarados (NO_DIFFERENCE sobre B1×B3 com B2 analisado não libera "estável ao longo do trimestre"); TEMPORAL_CONCENTRATION exige CONCENTRATED sustentado. Sinal `temporalComparison` carrega `relationValidationStatus/sampleDifference/trendSupported/analyzedBuckets/bucketCount/absenceEstablished`.
- **Aliases fechados** do status declarado pela análise (`TEMPORAL_STATUS_ALIASES` em interaction-tools.ts): grafias erradas observadas + aliases semânticos controlados (STABLE/NO_CHANGE/UNCHANGED → NO_DIFFERENCE_SUPPORTED; CHANGED/DIFFERENCE → DIFFERENCE_OBSERVED); desconhecido = INSUFFICIENT_EVIDENCE sem interpretação; a normalização fica registrada em `downgradedReason`. ### Investigação V1.3.4.2 — Temporal Output & Reference Integrity (2026-09-21, sem migration)

Hardening pequeno depois do BENCHMARK_BLIND_V4 (fecha o ciclo do dataset diagnóstico atual): **"nenhuma diferença sustentada" NÃO é "permaneceu estável"; posição de apresentação NÃO é handle.** Sem LLM juiz; sem mudança em Planner, rounds, budgets, ledger cap, E_SIGNAL_CONTEXT, verifier (que ficou mais estrito, nunca mais permissivo), absenceEstablished, wrong-relation gap. O que o código aplica:

- **Política de alias de status** (`TEMPORAL_STATUS_ALIASES` em interaction-tools.ts): alias só corrige grafia/typo ou abreviação do MESMO conceito (`NO_DEFFERENCE_SUPPORTED`, `NO_DIFFERENCE` → NO_DIFFERENCE_SUPPORTED). Palavras de RELAÇÃO no campo status (`STABLE`, `NO_CHANGE`, `UNCHANGED`, `CHANGED`…) não viram status: normalização `RELATION_AS_STATUS` → comparação `INSUFFICIENT_EVIDENCE` (nunca promovida), `statusNormalization/declaredStatus` na telemetria, a relação declarada em `findings` continua validada pela regra específica. A instrução da análise diz que status é exatamente um dos três valores e que estabilidade só existe como finding STABLE. Consequência: `E_TEMPORAL_COMPARISON` só é satisfeita por comparação válida do contrato (no V4, 6/9 comparações eram "STABLE" lido como NO_DIFFERENCE — agora ficariam abertas).
- **TemporalConclusion** (`temporal-semantics.ts`: `temporalConclusionOf/temporalConclusionOfLedger`, `TEMPORAL_SAFE_MEANINGS`, `renderTemporalConclusion`): a conclusão AUTORIZADA é derivada por código das comparações comportamentais validadas — `SUPPORTED_RELATION` (relações sustentadas → `allowedRelations`: STABLE→STABILITY, INCREASED/DECREASED→CHANGE/EARLIER_VS_LATER (+TREND com trendSupported), CHANGED/DIFFERENT_PATTERN→CHANGE, CONCENTRATED→TEMPORAL_CONCENTRATION) | `NO_DIFFERENCE_SUPPORTED` ("Não foi encontrada diferença temporal sustentada nas evidências analisadas.") | `SAMPLE_DIFFERENCE_ONLY` | `INSUFFICIENT_EVIDENCE` | `NOT_COMPARED`. Relação SUPPORTED dentro de comparação rebaixada a INSUFFICIENT não conta (consistente com `temporalFactsOf`). Vai ao dossiê da síntese ("CONCLUSÃO TEMPORAL AUTORIZADA (…): <formulação segura>"), à telemetria (`summary.temporal.conclusion`, QA Lab "Conclusão autorizada") e ao ledger (linha NO_DIFFERENCE diz que não é "permaneceu estável").
- **Gating transversal contra a conclusão** (`checkTemporalConclusionCompatibility`; `gateSynthesis` → `temporalCompatibilityRejections` sobre hipóteses sustentadas, premissas de recomendação e texto entregue; Orquestrador via `collectSpecialistTemporalAuthorization` + `gateOrchestratorClaims(…, { conclusions, acceptedRelations, indicatorTemporalFact, text })`): família de ESTABILIDADE (`detectStabilityLanguage`: "permaneceu/se manteve/continuou estável|constante", "mantendo(-se) … estável/estabilidade", "é estável ao longo…", "estabilidade ao longo/nos comportamentos"; negação na mesma oração e orações de gerúndio/conectores tratadas; "manteve o cliente informado", "comunicação constante", "desvios constantes" não entram) só passa com claim STABILITY aceita, relação STABLE sustentada ou indicador com sinal STABLE; família de MUDANÇA (`detectChangeLanguage`) só com relação/claim de mudança ou fato comparativo de indicador. Motivo novo `TEMPORAL_CONCLUSION_INCOMPATIBLE` (quando houve comparação; sem comparação continua `TEMPORAL_RELATION_UNDECLARED`); claim STABILITY sobre fato NO_DIFFERENCE sem STABLE sustentado também é `TEMPORAL_CONCLUSION_INCOMPATIBLE`. 1 correção → fallback/descarte como sempre. O léxico é defesa secundária (também entra em `detectTemporalLanguage`); a fonte de verdade é conclusão + claims aceitas.
- **Ordinal × handle** (`transcript-projection.ts`): `EvidenceUnit.interactionOrdinal` (posição de apresentação, explícita) ≠ `interactionRef` (handle). Cabeçalho model-facing `=== Interação #3 (ref: I6 · B2 · data; assunto: …) ===` + instrução "interactionRef é sempre o ref; se só souber a posição, use interactionOrdinal". `resolvePresentationOrdinal` traduz SÓ referência ordinal explícita pela ordem de apresentação (ordem de inserção do mapa model-facing); `I3` é sempre I3 (handle vence mesmo com ordinal junto); ordinal fora da apresentação = WRONG_INTERACTION; depois da tradução o verifier continua estrito (literal na interação apresentada, falante, ANY/ALL, privacidade — nada de quote search entre interações). Telemetria `referenceResolution` HANDLE|PRESENTATION_ORDINAL por unidade válida, `ordinalResolvedCount/ordinalResolutionRejectedCount` na verificação. Regex dos harnesses de benchmark aceita `#n`.
- **Replay determinístico** (`scripts/poc-tools/benchmarks/blind-benchmark-replay-v1342.ts` → `replays/diagnostic-v1_1-v1341/v1342-temporal-output/replay.json`, V4 intocado): 6 status "STABLE" → INSUFFICIENT (necessidade satisfeita 9 → 3); as 4 sínteses "estável" do V4 bloqueadas 4/4, os outros 5 NO_DIFFERENCE continuam válidos, 12 sem comparação inalterados; 0 unidades com ordinal explícito (0 resoluções possíveis pela regra), 16 WRONG_INTERACTION continuam legítimos (12/16 coincidem com a POSIÇÃO da interação que contém o trecho — o erro que o cabeçalho `#n` passa a prevenir).
