### Central de Dados — porta única de entrada dos dados do cliente (implementada 2026-09-16)

Módulo `backend/src/modules/data-hub` + área admin `/admin/data-hub` + Wiki `/wiki/central-de-dados` (ver `docs/dev/central-de-dados-ingestao.md`). Princípio: **conectores genéricos + contratos de dados + mapeamento + validação + domain writers** — nunca "uma integração por indicador": o feed de medições recebe qualquer `indicatorCode` do catálogo; um Grupo novo é configuração. Cadeia obrigatória: Fonte → Feed → Conector (CSV/Excel upload, API Pull, API Push, SFTP) → Raw/Staging (`data_raw_objects`, retenção 30 dias) → Mapping (declarativo, sem JS/IA) → Contrato (`EMPLOYEES@1`, `INDICATOR_MEASUREMENTS@1`… registro único em `domain/contract-registry.ts`) → Validação (estrutura + referências EM LOTE; referência inexistente = quarentena, nunca pai fake) → Writer (upsert multi-linha pela chave natural; reutiliza `enrollIndicatorWorkflows`/`enrollFlagWorkflows`/outbox/`applyEmployeeStatusSnapshot`) → Run + Quarentena + Lineage. Preview/amostra/teste nunca escrevem. Três conceitos que nunca se misturam: status da fonte (DRAFT/ACTIVE/PAUSED/ERROR), saúde da conexão (HEALTHY/ERROR/UNKNOWN) e atualidade (FRESH/STALE/NEVER, por cadência) — "conectado ≠ atualizado". Segredos: AES-256-GCM com `DATA_HUB_SECRET_KEY` fora do banco, nunca devolvidos/logados; tokens de push só por hash (valor uma vez). Identidade: `people.matricula`, `teams/subteams.external_code`, `interactions.external_id`. Um feed autoritativo ativo por contrato mestre; ausência nunca desativa. Migrations 056 (tabelas `data_*`, códigos externos, uniques naturais de goals/turnos) e 059 (índice FK de matrículas por medição). Prova contra o banco de teste: `INIA_DB_PROOF=1 npx vitest run data-hub-proof` (CSV/Excel/indicador dinâmico/API Pull 2 páginas + checkpoint/API Push idempotente/SFTP fake/schema change/segredos/side effects/100k medições). Teste de sincronia Wiki × registro em `contract-registry.test.ts`.

Hardening situação funcional (2026-09-16, migration 061): EMPLOYEES (snapshot) e EMPLOYEE_ABSENCES (períodos explícitos) alimentam a MESMA camada canônica via `applyEmployeeStatusSnapshot`; precedência por evidência (período explícito > feed autoritativo > evidência mais nova), conflito vira aviso `DATA_EMPLOYMENT_STATUS_CONFLICT` na quarentena (nunca silencioso, nunca rejeição); base do status `EXPLICIT_PERIOD | OPEN_PERIOD | PRESUMED_AFTER_PERIOD | PRESUMED_NO_HISTORY` (sem enum UNKNOWN: ACTIVE presumido nunca é certeza); projeção diária `runEmploymentStatusProjection` (ticker do server, fuso da org, idempotente, zero LLM). Freshness da situação funcional (`employment-status-freshness.ts`) = FRESH/STALE/UNKNOWN derivada só dos feeds de situação da Central (conexão saudável ≠ situação atualizada); elegibilidade carrega `statusConfidence`; Condition/Ranking distinguem `NO_VALUE` (não produziu) × `NO_ELIGIBLE_DAYS` (não deveria) × `EMPLOYMENT_STATUS_STALE` (não sei com segurança) e medição real nunca é invalidada. Wizard aceita `?sourceId=` ("+ Adicionar feed" na fonte: reutiliza conexão e segredos, começa no contrato). Prova: `INIA_DB_PROOF=1 npx vitest run employment-status-hardening`.

Situação real + escala real (2026-09-16, migrations 062–064): as NOVE situações funcionais do negócio (`EM_PRODUCAO | TRANSFERIDO | FERIAS | INSS | PILOTO | MATERNIDADE | PATERNIDADE | APOSENTADO | ATIVIDADE_OFF`, rótulos pt-BR) com regra POSITIVA única — só `EM_PRODUCAO` é elegível (`isOperationallyEligibleStatus`), nunca lista negativa; legado ACTIVE/VACATION/LEAVE/INACTIVE continua aceito no banco (dual-read `toCanonicalEmploymentStatus`, backfill ACTIVE→EM_PRODUCAO, VACATION→FERIAS, LEAVE/INACTIVE→ATIVIDADE_OFF com `legacy_status`, `raw_status` sempre preservado); `normalizeEmploymentStatus` só mapeia explícitos (código/rótulo/ACTIVE/VACATION) — valor próprio da fonte entra por "Mapear códigos", desconhecido = `DATA_EMPLOYMENT_STATUS_UNKNOWN`, nunca "em produção por palpite". Escala: regime 5x2/6x1 é metadata (`employee_work_shifts.schedule_type`, com vigência); a evidência é o calendário por dia `employee_schedule_days` (contrato `WORK_SCHEDULE_DAYS` "Escalas de trabalho"; ausência de linha NÃO é folga); `people/domain/work-schedule.ts` decide: explícito > 6x1 sem folga = `UNKNOWN_SCHEDULE` (nunca seg–sex inventado) > fallback `LEGACY_WEEKDAY_FALLBACK` seg–sex com feriado (`organization_holidays`, Administração › Central de Dados › Calendário operacional) só aqui — escala explícita vence feriado. Regra final em `resolveEligibleDaysBySubject` (único): admitido ∧ EM_PRODUCAO ∧ escala trabalha ∧ sem exclusão; sábado/domingo podem ser elegíveis, folga em dia útil não; resultado rico (calendarDays/scheduledWorkDays/excludedByStatus com rótulo/excludedByScheduledDayOff/Holiday/UnknownSchedule/scheduleConfidence). Motivos `WORK_SCHEDULE_STALE`/`WORK_SCHEDULE_UNKNOWN` ≠ `EMPLOYMENT_STATUS_STALE`; NÃO ELEGÍVEL ≠ zero; incerteza ≠ performance ruim. Severidades: `warning_count` (avisos de registros aplicados, ex.: conflito) separado de `error_count`/`records_rejected`. Lineage visível ("Origem do dado", `lineage-sheet.tsx`) no Admin › Usuários e no perfil (capability `canManageDataHub`, V1.5.8). Massa demo: operadores 0011–0022 cobrem as nove situações, 0021–0025 as escalas (6x1 folga quarta/trabalha sábado e domingo; 6x1 folga domingo + INSS; 5x2 seg–sex; 5x2 ter/qua; 6x1 sem calendário). Provas: `eligibility.test.ts` (54) + `INIA_DB_PROOF=1 npx vitest run employment-status-hardening` (13).

Calendário operacional fechado (2026-09-16, migrations 065–067): MEDIÇÃO SÓ EM DATA ELEGÍVEL — as datas elegíveis do resolvedor único entram na consulta de medições como intervalos por pessoa (`eligibleDayRanges` + `eligibleMeasurementSql`, filtro `where m.eligible` em TODAS as agregações: numerador/denominador, taxa, média/amostra, soma, LATEST = último valor em data elegível, reincidência); medição de folga/day off/férias fica no banco e fora do cálculo (`ignoredMeasurements` no trace e no perfil); cobertura e valor olham o mesmo universo; DAILY/HOURLY/INTERACTION recebem a regra diária, MONTHLY/CUSTOM mantêm o comportamento anterior. EXCEÇÕES (`employee_schedule_exceptions`, contrato `WORK_SCHEDULE_EXCEPTIONS`): day off/banco de horas/folga extraordinária vencem a escala por `effect = NON_WORKING` (nunca por código), sem reescrever o calendário; folga normal do 6x1 NÃO é exceção; `active=false` cancela sem apagar. Precedência única por dia: admissão → situação → exceção → escala explícita → 6x1 sem calendário (desconhecido) → fallback seg–sex. CAPITAL OPERACIONAL: reference data das 27 capitais (`brazilian_capitals`, people/domain/brazilian-capitals.ts) + `people.operational_capital_code` = jurisdição de feriados (nunca endereço/lotação/teletrabalho); EMPLOYEES aceita `operationalCapitalCode`; UF derivada. FERIADOS: catálogo-base `holiday_catalog` 2026–2028 com proveniência (`npm run db:seed:reference`, reference-data/holiday-catalog-data.ts, lacunas em `HOLIDAY_CATALOG_GAPS`, ponto facultativo nunca) + `organization_holidays` como overlay; aplicabilidade NATIONAL/STATE(UF)/MUNICIPAL_CAPITAL; política `holiday_fallback_policy` IGNORE (default) | EXCLUDE_APPLICABLE_HOLIDAYS só no fallback — escala explícita sempre vence feriado. HORIZONTE da escala (`resolveWorkScheduleHorizon`, `schedule_horizon_warning_days`) ≠ freshness ≠ conexão: "Calendário disponível: de → até · termina em N dias" na Central/Qualidade/perfil. Provas: eligibility.test.ts (96), holiday-catalog.test.ts, `INIA_DB_PROOF=1 npx vitest run employment-status-hardening` (17).

Calendário operacional V1 FECHADO — PLANEJADO × OBSERVADO (2026-09-16, migration 068): a INIA não pergunta só "estava programado?" mas "houve evidência confiável de que trabalhou?". Evidência (`people/domain/work-activity-evidence.ts`, sem LLM): interação real do colaborador no dia OU medição diária de indicador com `indicator_definitions.proves_work_activity = true` (default false; configuração na tela Indicadores, nunca `if code === …`; anticircular: o indicador em cálculo só prova o dia se a própria definição estiver marcada). Dia resolvido (`people/domain/workday-resolution.ts`, função pura única): situação funcional é SOBERANA (produção com INSS/férias = inconsistência, a situação nunca muda) → EM_PRODUCAO + evidência = `WORKED_OBSERVED` (elegível mesmo em day off/banco/folga 6x1; o plano fica registrado em `observed.workedDespitePlan`, nunca apagado) → sem evidência vale o planejado; programado + turno encerrado (`shift_end`, ou fim da data local sem turno) + fontes configuradas + nada observado = `MISSING_EXPECTED_PRODUCTION` (continua elegível; vira PENDÊNCIA, nunca exceção automática). `resolveWorkdaysBySubject` alimenta `resolveEligibleDaysBySubject`, o Calendário da equipe e o job `workday-reconciliation-service.ts` (5 min, idempotente, `workday_reconciliations` única por pessoa × dia × kind; alertas `WORKDAY_*` no sino; auto-resolução quando a carga atrasada chega ou o plano muda). Supervisor resolve na Surface Pendências (kind `WORKDAY_RECONCILIATION`): Não trabalhou (motivo → exceção auditável) / Trabalhou — dados não chegaram (nada inventado) / Corrigir escala (`AJUSTE_ESCALA` por cima, escala da fonte intacta). Exceções ganharam origem (`CENTRAL_DATA | SUPERVISOR_MANUAL`), auditoria em `audit_logs` e provisionamento pelo Supervisor (`/api/v1/team-calendar`, aba "Calendário" do perfil para Supervisor+/Admin — não é WFM); códigos + `ATESTADO` (só motivo, nunca CID) e `AJUSTE_ESCALA`; conflito Central × Supervisor nunca sobrescreve (aviso `DATA_SCHEDULE_EXCEPTION_CONFLICT`). Horizonte da escala vira alerta administrativo (`WORK_SCHEDULE_HORIZON`, dedupe por org × admin × coverageUntil, resolvido quando avança). Bootstrap oficial `npm run db:bootstrap` = migrations → reference data (`holiday_catalog.verification`) → demo (nunca em produção); catálogo de feriados expõe cobertura verificada + `HOLIDAY_CATALOG_GAPS` na Central/Calendário operacional (nunca "100% completo"). Provas: `workday-resolution.test.ts`, `stale-unknown-consumers.test.ts` (todos os consumidores), `INIA_DB_PROOF=1 npx vitest run workday-reconciliation-proof` (9), `DEMO_SEED_CHECK=1` (bootstrap do zero).

Último hardening — DISPONIBILIDADE × CLASSIFICAÇÃO (2026-09-17, migration 069): **fim do turno ≠ dado fechado; ausência de dado ≠ ausência do colaborador.** Cada feed relevante da Central declara `availability_policy` = `{lagDays, availableByLocalTime}` (fuso da org; `data-hub/domain/data-availability.ts`, `expectedAvailableAt`); indicador pode ter override só se o feed mistura SLAs. Conceito distinto de freshness/saúde/horizonte. Por dia (organização, memoizado — nunca por pessoa) `people/domain/workday-data-availability.ts` combina evidência (só fontes `WorkActivityEvidence`; o ÚLTIMO prazo decide) e RH (EMPLOYEES/EMPLOYEE_ABSENCES; sem feed = nada a esperar): `READY | WAITING_FOR_SOURCES | DATA_SOURCE_DELAY | AVAILABILITY_UNKNOWN`. Sem política a INIA NÃO assume D+1 e não conclui ausência. `resolveWorkday` (precedência explícita: situação não produtiva → trabalho observado → classificação humana → exceção/plano → escala → fallback → desconhecido) só produz `MISSING_EXPECTED_PRODUCTION` com fontes fechadas; antes disso `WAITING_FOR_SOURCES`; prazo vencido sem carga = `DATA_SOURCE_DELAY` → alerta administrativo `DATA_SOURCE_AVAILABILITY_DELAYED` por fonte × dia (nunca 2.000 pendências). CLASSIFICAÇÃO (`workday_classifications`, `people/domain/workday-classification.ts`, uma linha por revisão, `supersedes_id`/`superseded_reason`, auditoria, sem coluna clínica): `UNJUSTIFIED_ABSENCE` (dia CONTINUA esperado/elegível), `JUSTIFIED_ABSENCE` + motivo (fora), `WORKED_DATA_MISSING` (elegível, nada inventado) — nunca exceção de calendário, nunca IA. Revisável ("Editar classificação" no Calendário da equipe, `POST /team-calendar/classifications`); produção tardia → `CONTRADICTED_BY_WORK_EVIDENCE`; RH tardio (férias/INSS) → `SUPERSEDED_BY_AUTHORITATIVE_STATUS`; RH confirmando EM_PRODUCAO não apaga atestado manual. Política por indicador `unjustified_absence_policy` = `NO_SAMPLE` (default: TMA/Qualidade sem zero falso) | `ZERO_CONTRIBUTION` (só soma/média de contagens; contribuição lógica 0 via `applyZeroContribution` — NUNCA linha em `indicator_measurements`; Produção 0 é resultado conhecido, entra em ranking). Central › Qualidade mostra SLA por fonte (freshness ≠ disponibilidade) e métricas de classificação. Provas: `data-availability.test.ts`, `workday-data-availability.test.ts`, `unjustified-absence.test.ts`, `workday-resolution.test.ts`, `INIA_DB_PROOF=1 workday-reconciliation-proof` (12). Demo: políticas em `seeds/demo/002_data_hub.sql` + `touchDemoAvailabilityFeeds`.

Fechamento (2026-09-17, migration 070): (1) **Clock único** `shared/domain/clock.ts` (`Clock`, `systemClock`, `fixedClock`; `data-hub/application/ports.ts` reexporta) — instante absoluto, distinto do fuso da organização (leitura civil). Entradas dos jobs recebem Clock (`runWorkdayReconciliation`, `runScheduleHorizonAlerts`; `reconcileOrganizationWorkdays` recebe `now`), e todo timestamp de decisão escrito pela aplicação (detected_at, resolved_at, classified_at, superseded_at, created_at/resolved_at de alertas, queued_at/finished_at das cargas) vem do Clock, nunca de `now()` do banco; a Central conta "hoje" pelo Clock no fuso da org (warningsToday/runsToday determinísticos). (2) **Upgrade sem DELETE**: cada rodada do job reavalia TODA pendência "Produção não identificada" aberta pela regra atual (`legacyReviewOf`): WAITING → `SOURCES_STILL_OPEN`, DELAY → `DATA_SOURCE_DELAYED` (alerta de fonte permanece), situação não produtiva → `STATUS_NON_PRODUCTIVE`, produção → `PRODUCTION_RECEIVED_AFTER_ALERT`, classificação → resolução da classificação, plano → `PLAN_UPDATED_AFTER_ALERT`; só MISSING continua aberta; motivo em `snapshot.reviewedByCurrentRule`; idempotente; `npm run calendar:reconcile` roda uma rodada explícita na janela de upgrade (o servidor faz o mesmo ao subir e a cada 5 min). Prova: 10 pendências legadas → 8 resolvidas / 2 mantidas, 2ª rodada 0 (workday-reconciliation-proof). (3) **Indicador demo oficial** `ATENDIMENTOS` (`DEMO_VOLUME_INDICATOR`: SUM/COUNT/diário/evidência/ZERO_CONTRIBUTION, criado pelo mesmo contrato do catálogo em `ensureDemoVolumeIndicator`, medição diária = contatos do dia) + fixtures 0029 (falta injustificada vigente em D-2, dia útil) e 0030 (falta injustificada contrariada por evidência em D-3); `db:bootstrap:check` prova 4 medições + 1 zero lógico, TMA 4 amostras, atestado → 4/4, nada criado/apagado. (4) **Lista do Calendário da equipe com filtros e paginação** no padrão das listagens administrativas (`ListToolbar`/`ListSelectFilter`/`ListPagination`/`useAdminListState`): `GET /team-calendar` aceita `search`, `teamId`/`subteamId` (grupo/subgrupo do operador, opções derivadas da equipe), `jobTitle` (multi — cargo = `people.job_title`, opções derivadas da própria equipe em `filterOptions`), `scheduleType` (5x2/6x1/`NONE`), `attention` (`CALENDAR_ATTENTION_KINDS`: pendência, aguardando dados, fonte atrasada, falta injustificada, divergência, inconsistência), `scheduledToday` (true = dia de HOJE elegível, resolvido à parte quando o período visível não contém hoje) e `page`/`pageSize`; a resolução PLANEJADO × OBSERVADO continua rodando para todos os operadores diretos (o filtro é sobre o resultado, `applyCalendarFilters`, puro) e a resposta traz `pagination {page,pageSize,total,totalPeople}` + `provisionablePeople` (todos, para o seletor de provisionar). Todos os filtros da view são `ListSelectFilter`/`ListBooleanFilter` (seletores simples, mesmo desenho; o backend continua aceitando listas). Radix `DropdownMenu` (`ListMultiSelectFilter`) trava o event loop do jsdom ~13 s ao abrir — evitar em testes.

### Central de Dados — bancos de dados externos + instalação reproduzível (2026-10-06, migrations 119 + 120)

Regra: **banco INTERNO da INIA (PostgreSQL, `DATABASE_URL`, migrations) ≠ bancos EXTERNOS do cliente (só leitura, configurados pela tela).** Doc: `docs/dev/central-de-dados-bancos-externos.md`; Wiki `/wiki/central-de-dados/conectores#banco-de-dados`.
- **Conector `DATABASE`** (kind de fonte + conector de feed; segredo `DATABASE_PASSWORD` no cofre AES da Central): SQL Server (`mssql`), PostgreSQL (`pg`), MariaDB e MySQL (`mysql2`). Domínio em `data-hub/domain/database/*` (motor/TLS/config, categorias de coluna, dialetos com keyset, modo de leitura + checkpoint + `planPage`, normalização de valores, classificação/sanitização de erros); adaptadores em `infrastructure/external-databases/*` (sessão somente leitura pelo próprio banco, limites de tempo, 2 operações por conexão); `application/connectors/database-connector.ts` (teste de rascunho sem gravar, descoberta ≤ 2.000 objetos, colunas, amostra de 20) e `application/database-run.ts`. Só tabela/visão escolhida (nunca SQL livre); nunca cria/altera nada no banco do cliente.
- **Leitura**: INCREMENTAL (campo de atualização + chaves de desempate) ou FULL; posição = texto exato das colunas de ordenação. Contratos de evento/medição = página a página, cada página aplicada numa transação com quarentena, lineage, contadores e checkpoint; cadastro mestre/ATOMIC/feed íntegro/FULL sem chave = de uma vez, checkpoint só depois de concluir. Limite por carga → carga `CONTINUATION`; carga interrompida → `recoverInterruptedRuns`; "Ler tudo de novo" zera a posição. Esquema muda → `DATA_SCHEMA_CHANGED`; erros novos `DATA_SOURCE_TLS_FAILED | PERMISSION_DENIED | NOT_FOUND | VOLUME_LIMIT`.
- **Tela**: "Conectar banco de dados" (assistente de 6 etapas `components/admin/data-hub/database/*`: banco → conexão + Testar → tabela/visão → conjunto + leitura → amostra + mapeamento sugerido por nome E pelo tipo dos valores (`suggestMapping(contract, columns, sampleRecords)`) com confirmação obrigatória dos obrigatórios → validar e ativar); "Adicionar outro conjunto desta conexão" reaproveita a senha.
- **Instalação** (`backend/src/infrastructure/installation/*`, raiz `package.json`, `compose.yaml`, `scripts/install/*`): `npm run install:all` → `env:init` (segredos aleatórios; porta livre automática para o PostgreSQL do Docker; `-- --postgres-port N` troca só a porta numa instalação existente) → `db:up` → `doctor` (detecta OUTRO PostgreSQL respondendo na porta) → `setup` (migrations → referência → limpeza do que as migrations semeiam → organização + 1º Administrador geral com senha TEMPORÁRIA, marcador `installation_info` da migration 120; `--demo` = demonstração, recusada sem ela) → `dev` | `build` + `start`. `update` = só migrations pendentes; `admin:create` = outro administrador. Uma organização por instalação (id fixo `00000000-0000-4000-8000-000000000001`). Compose: `postgres` interno + exemplos externos (`examples:up` PostgreSQL/MariaDB/MySQL; `examples:sqlserver:up` em perfil próprio, x86/Rosetta; `examples:down` nunca para o banco interno). O pool do banco interno tem tratador de `error` (PostgreSQL reiniciado não derruba a API).
- Provas: `data-hub/domain/database/database.test.ts`, `INIA_DB_PROOF=1 INIA_EXTERNAL_DB_PROOF=1 NODE_ENV=test npx vitest run external-database-proof` (10 cenários por banco; PostgreSQL/MariaDB/MySQL 30/30), `INIA_DB_PROOF=1 NODE_ENV=test npx vitest run installation-proof`, frontend `database-wizard.test.tsx`. Instalação limpa validada de um clone (2026-10-06). **SQL Server NÃO validado contra servidor real** (sem Rosetta no Mac de teste).
- **Dois servidores (2026-10-07, POC da empresa: aplicação numa área, dados em outra):** o banco INTERNO continua PostgreSQL, hospedado na área de dados; o SQL Server dos clientes é só fonte (Central de Dados). `node scripts/install/env-init.mjs --own-postgres --public-url https://inia.empresa.local` (ENDEREÇO ÚNICO com IIS/proxy na frente: `CORS_ORIGIN` e `NEXT_PUBLIC_INIA_API_URL` = origem pública, API e interface só em 127.0.0.1 — `HOST` no backend (`env.ts`/`server.ts`) e `INIA_WEB_HOST` lido pelo `run.mjs`; `https://` → `NODE_ENV=production`, `http://` → development; rodar de novo troca o endereço e exige `npm run build`; alternativa sem proxy `--app-url/--api-url` = duas portas abertas; chamado com `node` direto porque no PowerShell o `--` do `npm run x -- …` pode ser engolido) → `npm run db:connect` (`scripts/install/db-connect.mjs` + `internal-database.mjs`: interativo ou por opção com `INIA_DB_PASSWORD`; criptografia `disabled`/`encrypted` = `sslmode=no-verify`/`verified` = `verify-full` + `--ca`, e conferida exige o NOME do servidor — com IP o driver não confere o nome do certificado; confere conexão, versão ≥ 15, UTF8, permissão no schema public, extensões `pgcrypto`/`btree_gist` (confiáveis: o dono do banco cria) e estado; só grava DATABASE_URL se tudo passar; nunca imprime a senha). `doctor` usa as mesmas verificações; `setup`/`update`/`admin:create` recusam endereço que não seja PostgreSQL.
