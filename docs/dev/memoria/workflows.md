### Workflows-modelo: DRAFT válido, destinatários e editor (hardening 2026-09-16)

"DRAFT válido" = rascunho que passa 100% na validação do botão Publicar sem ser publicado. A validação é UMA função (`workflows/application/validate-workflow-for-publish.ts`), usada por `POST /:id/publish` e pelo dry-run `POST /admin/workflows/:id/validate` (`{ valid, error: { code, message, nodeId } }`, zero escrita); o editor espelha as mesmas regras em `schemas/admin/workflow-validation.ts`. Os 22 modelos estão exportados literalmente em `backend/src/modules/workflows/testing/official-model-workflows.json` — fixture única dos testes de catálogo (backend: validação inteira; frontend: validador do editor) — ver `docs/dev/workflows-modelo.md` para reexportar.

Regras que o código aplica: "O próprio operador" só em contexto EMPLOYEE; fora do caminho individual o Output vai para a gestão, resolvido **pela estrutura** (`workflows/application/organizational-recipient.ts`, port `OrganizationalHierarchyReader` com implementação Postgres e em memória): âncora-pessoa com o cargo → ela; senão cadeia acima/descendentes com o cargo; Grupo/Subgrupo → ancestrais de TODOS os operadores membros. Exatamente 1 → ok; 0 → `WORKFLOW_OUTPUT_RECIPIENT_NOT_FOUND`; 2+ → `WORKFLOW_OUTPUT_RECIPIENT_AMBIGUOUS`. NUNCA "um membro qualquer". A mesma função roda no publish (dry-run), no runtime (`executeOutput` falha o node em vez de descartar o alerta; no caminho individual, cargo ausente na cadeia do operador também é erro) e no QA Lab (step mostra "Destinatário resolvido"). Grupo/Subgrupo não têm owner persistido — não inventar. Superfícies reais: `FOLLOW_UP` (Acompanhamento — para gestão vira alerta com o **conteúdo** na descrição, `describeOutputContent`) e `NOTIFICATION`; `INBOX` não tem leitor (Pendências real = só Revisão humana). Revisão humana: Aprovado → Output ao operador; Reprovado → não publica; Escalar → **Escalonar ao Gerente** com o conteúdo (`END_BRANCH` individual, `CONTINUE → Join` em fan-out) — nunca branch solto; num fan-out TODAS as decisões convergem no MESMO Join. Publish também bloqueia Agent/Orquestrador inexistente, inativo, agente-coordenador chamado direto e Orquestrador só de chat (`WORKFLOW_AGENT_*`/`WORKFLOW_ORCHESTRATOR_*`). JOIN vazio não chama IA (`skippedReason: "EMPTY_FAN_IN"`). Orquestradores têm política EXPLÍCITA persistida (migrations 053/054: `agents.specialty`, `assistant_orchestrators.policy_kind/policy_domains`) e aplicada por código em `assistant/domain/orchestrator-policy.ts` + router (422 ao vincular especialista proibido): de domínio = só o especialista do domínio + transversais explicitamente adicionados; multidomínio = domínios autorizados; gerencial = nenhum; INTERACTIVE = assistente do chat/voz (lista = autorização; só `invocation_mode = INTERACTIVE`). **Ativo ⇒ política definida** (constraint + 422 `ORCHESTRATOR_POLICY_REQUIRED`); `policy_kind` null só existe em legado INATIVO ("Sem política" na lista, switch travado até classificar). O editor de Orquestrador mostra incompatíveis desabilitados com o motivo. **Taxonomia alvo (migration 057, aditiva, dual-read/dual-write):** Agent = `specialty_kind` DOMAIN(+`domain`) | CROSS_CUTTING(+`capability`) | PERFORMANCE | SYNTHESIS(`consolidated_input`); Orquestrador = `routing_policy` DOMAINS(+`routing_domains` 1..N) | OPEN — "como escolhe especialistas" — separado de `invocation_mode` ("onde é acionado"); TRANSVERSAL/MANAGERIAL/INTERACTIVE são legado traduzido pelo dual-read. Regra de produto: sabe o especialista → `Chamar agente`; precisa escolher/combinar → Orquestrador; só sintetizar pós-JOIN → `Chamar agente` com Agent SYNTHESIS (`synthesis-agent-executor.ts`, 1 request, contrato estruturado) — os 7 modelos pós-JOIN já usam o Especialista de Síntese Gerencial. Especialista via Orquestrador com transcrição usa o mesmo contrato verificado do Agent direto. Template oficial ≠ instância: `testing/official-model-templates.json` declara o requisito organizacional (GENERIC/PERSON_ANCHOR/GROUP/GROUP_SCOPE) sem UUID; os 22 rascunhos são a instância demo. Editor: "Pronto para publicar" = validação local + dry-run `POST /:id/validate` sobre o rascunho salvo (`use-publish-validation.ts`; grafo sujo = stale, Publicar desabilitado fora de `ready`, backend revalida ao publicar). ### Gatilho Manual — "Executar agora" (2026-09-30, migration 100)

Quarto tipo nativo de gatilho: `{ kind: "manual", context: COLLABORATOR | INTERACTION | INDICATOR_MEASUREMENT, indicatorCode? }` (`workflows/domain/trigger-config-schema.ts`). O `context` declara QUAL dado real cada disparo traz; a **origem de dados** (`triggerDataOriginOf` no backend, `triggerDataOrigin` no frontend) é o que a publicação, o domínio do "Gerar feedback", o editor e o QA Lab perguntam — interação ≈ Flag, medição ≈ Indicador, colaborador ≈ Agenda individual — então as regras continuam as mesmas (Avaliação de processo/feedback de monitoria exigem interação; feedback/diagnóstico de indicador exige medição; colaborador exige `scheduledDataSource`; Condition sobre "valor do gatilho" só com medição; Manual nunca Consolidado nem Filtro Populacional). Salvar/publicar/reiniciar/ingerir nunca disparam (ingestão e agenda filtram pelo `kind`).
- **Disparo** (`workflows/application/manual-run.ts`): só Workflow Manual publicado, ativo e Individual; colaborador no escopo de `workflows.manage` de quem dispara (fora = 404) E elegível pelo Workflow (mesma `isOperatorEligibleForWorkflow`); interação da org, DO colaborador e com transcrição; medição PERSON do colaborador e do indicador do gatilho. Cria SÓ a matrícula normal parada no Gatilho da versão publicada (pinada), com exatamente uma origem (`interaction_id` | `indicator_measurement_id` + `matched_value_numeric` + estratégia pinada | `scheduled_subject_id` com `scheduled_for` nulo). `workflow_manual_runs` (quem, quando, versão, colaborador, interação/medição, `idempotency_key` unique por workflow × quem × chave) + `workflow_enrollments.manual_run_id` (unique) + evento `manual_run_requested` + `audit_logs WORKFLOW_MANUAL_RUN_REQUESTED`. Mesma chave = mesmo disparo (também em corrida); mesma chave com outro pedido = 409; chave nova = nova execução. O disparo novo acorda o worker do motor (`signalWorkflowWork`, ver "Motor de Workflow — execução concorrente"); o reenvio não faz nada.
- **API** `/api/v1/admin/workflows/:id/manual-run` (impedimentos, contexto, últimos disparos) · `/manual-run/collaborators|interactions|measurements` · `POST /manual-runs` · `GET /manual-runs/:runId` (estágio QUEUED/PROCESSING/RETRYING/WAITING/COMPLETED/FAILED + entregas persistidas; Avatar PENDING = convite, DELIVERED só após a fala). ### Motor de Workflow — execução concorrente e posse da matrícula (2026-10-05, sem migration)

Regra: **várias execuções de Workflow rodam ao mesmo tempo e uma execução longa nunca segura as outras nem roda em dobro.** Caso real que motivou (dev, 2026-10-05): uma investigação de indicador de ~12 min rodou TRÊS vezes em paralelo (a lease de 120 s vencia no meio do nó e o tick seguinte reivindicava a mesma matrícula) e o tick sequencial deixava os outros workflows do lote esperando.
- **Fila = a própria tabela** `workflow_enrollments` (vencida = `next_eval_at <= now()`; livre = `claimed_until` nulo ou vencido) — nenhum broker externo. `claimDueEnrollments` (`engine.ts`): `skip locked`, posse com o relógio do BANCO, **rodízio entre workflows** (`row_number() over (partition by workflow_id)`: a 1ª vencida de cada workflow antes da 2ª de qualquer um) e limite de vagas por workflow contando as que já rodam.
- **Posse durante o nó** (`processClaimedEnrollment` → `holdEnrollmentLease`): token = `claimed_until` exato (texto ISO UTC com microssegundos); compare-and-swap antes do nó e **heartbeat** a cada 1/3 da lease (120 s) enquanto ele roda — cada batida é outro CAS, então nunca ressuscita matrícula concluída/decidida/reivindicada por outro. Worker morto = sem batidas = lease vence = retomada pelo claim normal. Teto de 60 min de posse renovada (nó travado → aviso `workflow_enrollment_lease_hold_limit`, lease vence, outro worker retoma). `processEnrollment` continua sendo o único executor de nó.
- **Worker contínuo** (`workflow-worker.ts`, iniciado em `server.ts`): até `WORKFLOW_WORKER_CONCURRENCY` (padrão 8) matrículas em paralelo por processo; um workflow ocupa no máximo metade das vagas (fan-out de 2.000 colaboradores não trava outro grupo); vaga liberada é reaproveitada na hora — o próximo nó de um fluxo NÃO espera mais 60 s; varredura a cada 2 s + `signalWorkflowWork()` (disparo manual; o antigo `manual-run-pump.ts`, que rodava ticks extras sem limite no processo HTTP, saiu). Trava de laço quente (o editor não proíbe ciclos entre nós): > 30 nós da mesma matrícula em 60 s → 60 s fora do claim + aviso `workflow_enrollment_hot_loop`. Falha técnica de uma matrícula nunca derruba as outras. Desligamento: para de reivindicar e espera até 10 s; o que sobrar é retomado quando a posse vencer. Projeção de situação funcional + checador de agenda continuam a cada 60 s, agora sem sobreposição, e acordam o worker. Pool do Postgres: `DATABASE_POOL_MAX` (padrão 20).
- Várias instâncias do servidor podem rodar o worker no mesmo banco sem coordenação extra. Broker externo (Redis/RabbitMQ/SQS) só se um dia a varredura de 2 s não bastar — e mesmo assim a linha da matrícula continua sendo a fonte da verdade (o próximo passo natural é LISTEN/NOTIFY do próprio Postgres e um processo só de worker com o mesmo `startWorkflowWorker`).
- `runWorkflowTick` = UMA passada (provas/scripts) com as mesmas funções; execuções do lote em paralelo.
- Provas: `engine-lease.test.ts`, `workflow-worker.test.ts`, `INIA_DB_PROOF=1 npx vitest run workflow-engine-concurrency-proof` (Postgres real, lease de 1 s: nó longo não roda duas vezes; worker morto antes/no meio do nó é recuperado; workflow lento não segura outro; rodízio pelo SQL; duas instâncias = cada nó uma vez). Limite: um worker que perdeu a posse (sem conseguir renovar por > 120 s) não cancela o nó em andamento — a revisão otimista impede só o avanço duplo.

### Configuração em rascunho × publicada e confirmação de impacto (construída 2026-10-05, adotada 2026-10-15, migration 144)

Incidente em dev (05/10): trocar o gatilho de um Workflow ATIVO e publicado (Manual → "Por agenda", mensal dia 5 às 18:30, população ALL) gravava direto em `workflows.trigger_config`, que o checador lê — em 1 minuto ele recuperou o horário de hoje (catch-up do mesmo dia) e criou 2.264 matrículas com o grafo PUBLICADO antigo (canceladas como `dead`/`ACCIDENTAL_SCHEDULE_CANCELLED`, nunca apagadas). A correção ficou 10 dias sem commit no worktree `vigilant-poitras` (como migration 112, aplicada só no `inia_test`) e foi adotada em 15/10 sobre a base atual como **144** — a 112 foi desfeita no `inia_test` antes de aplicar a 144 (`inia` e `inia_test`). Regra: **Gatilho, Abrangência e Modo de avaliação (Estrutura Consolidada / Filtro Populacional) são RASCUNHO até Publicar; nada que o runtime lê muda por edição.**
- **Dois estados** (`workflows/domain/workflow-configuration.ts`): colunas `draft_trigger_config`, `draft_scope_type/team_id/subteam_id`, `draft_consolidated_structure`, `draft_population_filter` (irmãs de `draft_graph`) = o que o editor grava; as colunas vivas = configuração PUBLICADA, a única que `schedule-check.ts`, `flag-enrollment.ts`, `indicator-enrollment.ts`, `manual-run.ts`, o motor e a Central de Dados leem (nenhum leitor de runtime foi alterado). Escrita só por `workflow-configuration-store.ts › writeDraftConfiguration` (por grupo de campos — duas telas não se sobrescrevem; "Todos os elegíveis" vira null); em Workflow NUNCA publicado grava também o vivo (sem `active_version_id` não há runtime). Trigger SQL `workflows_sync_draft_configuration`: INSERT sem rascunho copia o vivo e UPDATE direto no vivo sem rascunho pendente leva o rascunho junto (seeds, scripts, provas e importadores que gravam SQL direto continuam coerentes); rascunho pendente nunca é sobrescrito.
- **Rotas** (`presentation/workflow-router/*`): `fetchScopedRow` devolve a linha com o rascunho no topo e a publicada em `live`; quem enxerga/edita = quem gerencia a Abrangência PUBLICADA (`canManageWorkflow`); `PATCH /:id` grava gatilho/Abrangência no rascunho (nome, descrição e ativo valem na hora) e só reavalia Orquestradores do RASCUNHO na troca de Abrangência; `PUT /:id/analysis-config` grava no rascunho e valida contra a Abrangência do rascunho.
- **Publicar** (`application/publish-workflow.ts`, ÚNICO caminho do rascunho para o vivo): trava a linha, valida com a MESMA `validateWorkflowForPublish` do dry-run (que agora confere também gatilho × Estrutura/Filtro — `validateDraftConfigurationModes`; `triggerAllowsConsolidatedMode/PopulationFilter` moram em `publish-validation/trigger-context.ts` e as rotas os reexportam de `shared.ts`), calcula o impacto, grava a versão COM a configuração (`workflow_versions.trigger_config/scope_type/team_id/subteam_id/consolidated_structure/population_filter`; a ativa de cada Workflow recebeu o vivo na migration, as anteriores ficam null) e copia rascunho → vivo + `active_version_id` na mesma transação (pool = begin/commit; client em transação = savepoint); `audit_logs WORKFLOW_PUBLISHED` com mudanças e impacto confirmado. Quem publica precisa gerenciar a Abrangência publicada E a do rascunho (403). "Descartar alterações de configuração" (`POST /:id/configuration/discard`) volta o rascunho ao publicado (grafo intacto; sem versão = 409 `WORKFLOW_NOT_PUBLISHED`).
- **Impacto de entrar no ar** (`application/go-live-impact.ts`): só Agenda nasce matrícula sozinha. `planDueScheduleEnrollments` (em `schedule-check.ts`; o checador insere com ele, em lote, por organização) é a mesma regra que a prévia conta — nunca duas regras de catch-up — e o impacto desconta slots já matriculados. Exige confirmação (`confirmationReasons`): `IMMEDIATE_CATCH_UP` (a 1ª rodada criaria matrículas hoje) ou `LARGE_POPULATION` (> `GO_LIVE_CONFIRMATION_POPULATION` = 50 por ocorrência E configuração nova para o runtime: 1ª publicação, configuração alterada ou ativação); Workflow inativo nunca. O pedido leva o `fingerprint` do impacto mostrado: sem ele/velho = 409 `WORKFLOW_PUBLISH_CONFIRMATION_REQUIRED` ou `WORKFLOW_ACTIVATION_CONFIRMATION_REQUIRED` com `details.impact`. **Ativar** (`PATCH active: true` de um publicado) usa a mesma regra sobre a configuração publicada. `GET /:id/publish-impact` = prévia sem escrita; `POST /schedule-preview` devolve `catchUpToday`.
- **API/UI**: listagem e detalhe = topo PUBLICADO + `draftConfiguration` (projeção com nomes) + `configurationChanges` (`TRIGGER|SCOPE|ANALYSIS`, vazio sem versão). Editor (`withDraftConfiguration`): canvas, validação, nó Gatilho e Configurações editam o rascunho; cabeçalho mostra o selo "Configuração não publicada"; "Executar agora" segue o PUBLICADO. Publicar (`use-publish-flow.ts`) busca o impacto e abre `go-live-impact-dialog.tsx` quando há mudança de configuração, confirmação exigida ou 1ª publicação de Agenda ("Entendi" obrigatório); 409 reabre com o impacto novo. Interruptor Ativar da lista = mesmo diálogo. `TriggerConfigEditor` só recomeça do gatilho salvo quando o CONTEÚDO muda (o refetch devolve outro objeto igual). QA Lab: "Testar rascunho" usa a configuração do rascunho, "versão publicada" a publicada (`withSimulationConfiguration`).
- **Paridade editor × backend**: o editor espelha "Estrutura Consolidada só com Agenda de calendário" (`validateConsolidatedTrigger`, código `WORKFLOW_CONSOLIDATED_MODE_INVALID_TRIGGER` no nó Gatilho); o Filtro Populacional × gatilho é só do backend (o editor não recebe o filtro; as rotas do rascunho já recusam a combinação).
